문제 정의The problem

AI는 "그럴듯한 코드"를 최적화한다

AI optimizes for plausible code

간단한 작업은 잘합니다. 12개 파일과 3개 서비스에 걸친 변경을 요청하면, 컴파일도 되고 그럴듯해 보이지만 기존 코드를 깨뜨리는 결과가 나옵니다.

Simple tasks go fine. Ask for a change spanning twelve files and three services, and you get something that compiles, looks right, and breaks everything it touches.

전형적인 실패 시퀀스The familiar failure

  • "Azure IoT용 Terraform 모듈 만들어줘"
  • AI가 즉시 2000줄을 생성
  • 의존성 누락, 변수명 불일치, 폐기된 패턴, 기존 인프라 파손
  • "Build me a Terraform module for Azure IoT"
  • AI immediately generates 2,000 lines
  • Missing dependencies, wrong variable names, outdated patterns, broken infrastructure

근본 원인Root cause

AI는 조사하는 것과 구현하는 것을 구분하지 못합니다. 코드를 요청하면 코드를 씁니다. 변수 명명 규칙이 기존 모듈과 맞는지 멈춰서 확인하지 않습니다.

AI cannot tell investigating from implementing. Ask for code and it writes code. It never stops to check whether the naming convention it picked matches your existing modules.

"AI writes first and thinks never."

해결책은 AI를 더 똑똑하게 만드는 것이 아니라, 특정 시점에 특정 행동을 못 하게 막는 것입니다. 제약이 목표를 바꿉니다.
The fix is not a smarter AI. It is preventing AI from doing certain things at certain times. The constraint changes the goal.
0:30~2:00 청중 공감 유도 구간. "AI가 만든 코드 디버깅하느라 몇 시간 쓴 적 있나요?" 질문으로 시작하면 좋음. 핵심 문장은 마지막 콜아웃.
0:30-2:00 Build empathy first. Opening with "who has burned hours debugging AI-written code?" works well. The closing callout is the key line.
정의Definition

HVE Core는 코드 라이브러리가 아니다

HVE Core is not a code library

Hypervelocity Engineering Core. 특화된 에이전트, 재사용 가능한 프롬프트, 자동 적용되는 코딩 표준, 검증된 스킬을 하나의 워크플로 시스템으로 묶은 AI 워크플로 자산 집합입니다.

Hypervelocity Engineering Core. A set of AI workflow assets that binds specialized agents, reusable prompts, auto-applied coding standards, and validated skills into one workflow system.

AI 아티팩트 4계층 위임 모델

The four-tier artifact delegation model

사용자 요청은 프롬프트에서 출발해 에이전트로 위임되고, 에이전트가 인스트럭션(표준)과 스킬(실행 능력)을 끌어옵니다.

A request starts at a prompt, is delegated to an agent, and the agent pulls in instructions (standards) and skills (executable capability).

핵심 개념 1 보충Key concept 1, continued

가장 흔한 오해: 인스트럭션 vs 스킬

The common confusion: instructions vs skills

둘 다 마크다운 파일이지만 성격이 정반대입니다. 이 구분을 놓치면 자산을 잘못된 계층에 만들게 됩니다.

Both are markdown files, but they are opposites. Miss the distinction and you build assets at the wrong tier.

수동적Passive

Instructions

  • 표준과 규칙을 제공
  • 파일 경로 glob 매칭으로 자동 적용
  • 여러 개가 동시에 겹쳐서 적용됨
  • 결과물은 Copilot을 위한 가이던스
  • Provide standards and rules
  • Apply automatically via path glob matching
  • Stack when several patterns match
  • Output is guidance for Copilot
vs
능동적Active

Skills

  • 실제 행동과 스크립트를 제공
  • 필요할 때만 명시적으로 로드
  • 자체 완결형 패키지 (스크립트·참조·자산)
  • 결과물은 실행된 작업
  • Provide real actions and scripts
  • Loaded explicitly, only when needed
  • Self-contained packages (scripts, references, assets)
  • Output is executed work

서브에이전트가 따로 있는 이유Why subagents exist

27개 서브에이전트는 부모의 컨텍스트를 오염시키지 않도록 별도 세션에서 실행되고 결과만 돌려줍니다. 코드 리뷰는 이 방식으로 7개 관점을 병렬 실행합니다.

The 27 subagents run in a separate session so they never pollute the parent context, returning only results. Code review uses this to run seven perspectives in parallel.

배포 대상 구분What actually ships

.github/instructions/ 최상위 파일은 저장소 전용이라 배포되지 않습니다. hve-core/, security/ 같은 패키지 하위 폴더에 있어야 배포됩니다.

Files at the root of .github/instructions/ are repo-specific and never distributed. Only files inside package subfolders such as hve-core/ or security/ ship.

5:15~6:15 "규칙 vs 행동", "자동 vs 명시적" 두 축만 기억하게 할 것. 질문이 자주 나오는 지점.
5:15-6:15 Leave them with two axes only: rules vs actions, automatic vs explicit. Questions cluster here.
핵심 개념 2Key concept 2

AI-DLC: 9단계 프로젝트 라이프사이클

AI-DLC: a nine-stage project lifecycle

설정부터 운영까지 각 단계에 담당 에이전트와 스킬이 매핑되어 있습니다. 리뷰·배포·운영은 구현으로 되돌아오는 피드백 루프를 가집니다.

Every stage from setup to operations maps to specific agents and skills. Review, delivery, and operations all loop back into implementation.

Design Thinking 9개 메서드는 3개의 종료 지점(문제 정의문 · 검증된 콘셉트 · 구현 스펙)에서 Stage 2로 합류합니다. 역할별 진입 가이드는 엔지니어·테크리드·TPM·보안 아키텍트 등 10종이 준비되어 있습니다.

The nine Design Thinking methods feed into Stage 2 at three exit points: problem statement, validated concept, and implementation spec. Ten role guides cover engineers, tech leads, TPMs, security architects, and more.

6:15~7:15 9단계를 다 읽지 말 것. "구현(6단계)이 가장 두껍고, 나머지는 그 앞뒤를 감싼다"는 구조만 전달. 피드백 루프 3개를 손으로 짚기.
6:15-7:15 Do not read all nine. Convey only that implementation (stage 6) is the thickest and the rest wraps around it. Point at the three feedback loops.
핵심 개념 3Key concept 3

RPI: 제약이 목표를 바꾼다

RPI: the constraint changes the goal

Research, Plan, Implement, Review. 구현 단계의 실제 엔진이며 HVE Core에서 가장 널리 쓰이는 방법론입니다.

Research, Plan, Implement, Review. The real engine behind the implementation stage and the most widely used method in HVE Core.

RPI 없이Without RPI

AI의 사고:
"이 변수명이 적당해 보이네. prefix를 쓰자."

What the AI thinks:
"That variable name looks reasonable. I will use prefix."

→
RPI 적용With RPI

리서치 증거:
"이 저장소의 기존 모듈 12개가 prefix가 아니라 resource_prefix를 쓴다. 확립된 패턴은 variables.tf에 있다."

Research evidence:
"Twelve existing modules use resource_prefix, not prefix. The established pattern lives in variables.tf."

AI가 지금은 구현할 수 없다는 것을 알면, "그럴듯한 코드" 최적화를 멈추고 "검증된 사실" 최적화를 시작합니다.

When AI knows it cannot implement right now, it stops optimizing for plausible code and starts optimizing for verified truth.

읽기 전용 리서치Read-only research

증거와 가정을 분리하고 출처 위치를 인용합니다. 코드를 쓰지 않습니다.Separates evidence from assumptions and cites source locations. Writes no code.

독립 계획 비평Independent critique

구현 전에 Pass / Revise / Blocked 판정을 남깁니다.Records a Pass, Revise, or Blocked verdict before implementation starts.

증거 기반 완료Evidence-based completion

증거가 있어야만 체크박스가 켜집니다.A checkbox flips only once evidence exists.

RPI 흐름RPI flow

리서치는 기본값이 아니라 조건부다

Research is conditional, not the default

먼저 "증거가 충분한가"를 판단합니다. 충분하면 리서치를 건너뛰고, 공백이 입증될 때만 리서치를 켭니다.

First judge whether the evidence is adequate. If it is, skip research; turn it on only when a gap is demonstrated.

3가지 진입 방법Three ways in

Follow-up은 새 단계가 아니다Follow-up is not a new phase

결함은 구현으로, 결정 공백은 계획으로, 증거 공백은 리서치로, 잔여 작업은 별도 항목으로 라우팅할 뿐입니다.

It only routes: defects to implementation, decision gaps to planning, evidence gaps to research, residual work to a separate item.

실행 상태(Complete/Partial/Blocked)와 결과(Conformant/Defects found/Not accepted)를 분리합니다. 실행 완료가 수용을 뜻하지 않습니다.
Execution status (Complete/Partial/Blocked) stays separate from outcome (Conformant/Defects found/Not accepted). Finishing execution is not acceptance.

왜 파일에 남기는가Why files, not chat

대화가 50K~200K 토큰으로 커지면 초기 지시(3K)가 최신 편향에 밀려 무시됩니다. 지시를 잊는 게 아니라 우선순위가 낮아지는 것입니다.

Once a conversation grows to 50K-200K tokens, the original 3K of instructions loses out to recency bias. The model does not forget them; it deprioritizes them.

그래서 컨텍스트를 /clear로 비워도 작업은 이어집니다. 맥락이 대화가 아니라 디스크에 있기 때문입니다.

That is why you can /clear and keep going. The context lives on disk, not in the chat.

정리Wrap-up

가져갈 것 세 가지

Three things to take away

01

제약이 품질을 만든다Constraints create quality

AI에게 더 많은 자유를 주는 게 아니라, 조사와 구현을 분리해 지금 할 수 없는 일을 정해주는 것이 핵심입니다.

The point is not giving AI more freedom. It is separating investigation from implementation and defining what it may not do right now.

02

맥락은 파일에 산다Context lives in files

대화는 길어질수록 열화합니다. 결정·증거·변경을 디스크에 남기면 언제든 컨텍스트를 비우고 이어갈 수 있습니다.

Conversations degrade as they grow. Put decisions, evidence, and changes on disk and you can clear context anytime and continue.

03

AI 자산도 검증 대상AI assets need validation

프롬프트·에이전트·스킬을 린트하고 테스트하고 평가하는 파이프라인이 있어야 팀 규모로 확장됩니다.

Scaling to a team requires a pipeline that lints, tests, and evaluates prompts, agents, and skills.
